# Latch Relay

General-purpose zero-knowledge WebSocket relay. Pure in-memory, no persistence — only does pairing matchmaking and encrypted message forwarding.

---

## Design Goals

1. **Zero-knowledge** — Bridge holds no keys, cannot decrypt message content
2. **Ephemeral** — Pure in-memory, no persistence; clients reconnect with channelId after restarts
3. **General-purpose** — Supports arbitrary applications via opaque peer IDs
4. **Many-to-many** — Each pairing creates a 1:1 channel; multi-peer is achieved through multiple channels (e.g. 1 CLI with 3 Apps = 3 channels), all multiplexed over a single WebSocket per peer
5. **Portable** — Protocol uses only widely available cryptographic primitives (P-256, PBKDF2, AES-GCM) so clients can be implemented on any platform, including resource-constrained IoT devices. Minimum requirement: ~64 KB available RAM (after RTOS/stack) for single-channel operation, ~80 KB for comfortable two-channel operation, corresponding to devices like ESP32 (520 KB SRAM) or STM32 with ≥384 KB total RAM

## Core Concepts

| Concept | Description |
|---------|-------------|
| **Connection** | A single WebSocket connection carrying an id; can serve multiple channels simultaneously |
| **Channel** | Long-lived 1:1 relay conduit; derived from shared key negotiation |

## In-Memory State

```
waitingPeers map[pairingId]*WaitingPeer    // pairing phase, deleted after match
channels     map[channelId]*Channel        // relay phase, see Channel Lifecycle
connections  map[*websocket.Conn]*Connection  // all active WebSocket connections
```


## Protocol

All communication happens over a single WebSocket endpoint. Pairing and relay messages are multiplexed on the same connection, distinguished by `type` and routed by `ch` (pairingId during pairing, channelId during relay).

### Phase 1: Pairing (SPAKE2)

Both sides share an 8-character pairing code. They perform a [SPAKE2](https://www.rfc-editor.org/rfc/rfc9382.html) password-authenticated key exchange through Bridge (see [Why SPAKE2](#why-spake2)). Ciphersuite: **P256-SHA256** (RFC 9382 §4), using the M and N points defined therein. Each pairing is strictly 1:1 (one waiting peer per pairingId).

```
CLI                          Bridge                         App
 |                             |                              |
 | WS /v1/connect              |              WS /v1/connect  |
 |   (persistent connection)   |          (persistent connection)
 |                             |                              |
 | pair {ch,pubShare,id}       |                              |
 |  ---------------------------->   store in waitingPeers map  |
 |                             |                              |
 |                             |  pair {ch,pubShare,id}       |
 |                             |  <----------------------------
 |                             |                              |
 |        Bridge: lookup waitingPeers[ch]                      |
 |        - if exists: match found -> exchange public shares   |
 |        - else: store as waiting peer                        |
 |                             |                              |
 |<-- pair_matched ------------|------ pair_matched --------->|
 |    ch, pubShare: Yb         |       ch, pubShare: Ya       |
 |    id: "device-xyz"         |       id: "sess-abc"         |
 |    role: "initiator"        |       role: "responder"      |
 |  (id is the OTHER peer's id from their pair message)       |
 |                             |                              |
 | SPAKE2 key agreement (RFC 9382, P-256):                     |
 |   w  = OS2IP(HKDF-Expand(seed, "spake2-w", 48)) mod n      |
 |   Both peers: pubShare = w*M + g^scalar  (random scalar)    |
 |   Note: Both peers blind with M (symmetric variant).        |
 |   Role is unknown at pubShare time; assigned by Bridge.     |
 |   Role differentiation is in the TT transcript, not M/N.   |
 |   Both compute K = scalar * (peerShare - w*M)               |
 |   Ke = Hash(TT)  where TT = transcript per RFC 9382         |
 |   ISK = HKDF-Extract(salt="latch-relay-isk"||pairingId, ikm=Ke)
 |                             |                              |
 | channelId = HKDF-Expand(ISK, "channel", 32)                |
 | encKey    = HKDF-Expand(ISK, "encrypt", 32)                 |
 |                             |                              |
 | Join channel with challenge-response (see Phase 2):         |
 |-- join {ch,id} ----------->|<-- join {ch,id} -------------|
 |   Bridge: delete waiting peer, begin channel challenge-response
```

#### SPAKE2 Context Binding

The SPAKE2 `context` parameter MUST include the pairingId to prevent cross-pairing relay attacks:

```
context = "latch-relay-v1" || pairingId
```

#### SPAKE2 Identity Binding

The SPAKE2 transcript (TT) includes peer IDs from the `pair_matched` message:

```
idProver   = initiator's id (from pair message)
idVerifier = responder's id (from pair message)
```

If a malicious Bridge modifies IDs in transit, the two peers compute different transcripts → different ISKs → pairing fails (detected by join timeout).

#### pairingId Derivation

Both `pairingId` and the SPAKE2 password scalar `w` are derived from a single PBKDF2 call, then separated via HKDF-Expand:

```
window = floor(unix_timestamp / 600)
seed   = PBKDF2-SHA256(
    password   = uppercase(code),
    salt       = "latch-relay-room-v1" || str(window),
    iterations = 100000,
    dkLen      = 32
)
pairingId = hex(HKDF-Expand(seed, "roomId", 32))
w         = OS2IP(HKDF-Expand(seed, "spake2-w", 48)) mod n
```

`seed` (PBKDF2 output) is used directly as the PRK for HKDF-Expand without an additional HKDF-Extract step, since PBKDF2 output is already uniformly distributed. `w` uses 48-byte output (384 bits) to avoid modular bias when reduced mod n (P-256 order, 256 bits). `OS2IP` is the octet-string-to-integer conversion from RFC 8017.

The joining peer tries the current window first; if no waiting peer is found, it retries with `window - 1` to handle boundary timing. At most two PBKDF2 evaluations per join attempt. Clients MUST have clock accuracy within ±10 minutes (NTP synchronization recommended for IoT devices).

See [Why PBKDF2 for pairingId](#why-pbkdf2-for-pairingid) for security rationale and performance characteristics.

#### Pairing Code Format

```
8 characters from [A-Z2-9] (31 chars, excluding 0/O/1/I/L to avoid visual ambiguity)
Display format: XXXX-XXXX
Entropy: 31^8 ≈ 8.5 × 10^11 ≈ 39.6 bits
```

After receiving `pair_matched`, both peers compute ISK, derive channelId and encKey, then join the channel (Phase 2). If the pairing code was wrong, ISK differs → different channelIds → peers never meet, detected by join timeout (30s).

#### Role Assignment

The first peer to send `pair` for a given pairingId is the **initiator**; the second is the **responder**. Bridge communicates this via the `role` field in `pair_matched`. Roles map to SPAKE2's Prover/Verifier distinction.

### Many-to-Many

Each pairing creates exactly one channel. Multi-peer is achieved through multiple independent channels, all multiplexed over a single WebSocket per peer:

```
App ── WS ── Bridge ── WS ── CLI1   (channelId_1, encKey_1)
                     ── WS ── CLI2   (channelId_2, encKey_2)
                     ── WS ── CLI3   (channelId_3, encKey_3)

App sends to CLI2: encrypt with encKey_2, send on ch=channelId_2
```

Each channel has its own encKey. Pairing with additional peers reuses the existing connection.

### Phase 2: Relay

#### Joining a Channel (Challenge-Response)

All channel joins — whether after initial pairing or on reconnection — use a unified challenge-response protocol. This proves the joining peer holds `encKey` without Bridge ever learning it.

```
Peer A                    Bridge                    Peer B
  |                         |                          |
  |-- join {ch,id} -------->|                          |
  |                         |  generate nonce_A (32B)  |
  |<-- challenge {ch,       |                          |
  |    nonce} --------------|                          |
  |                         |                          |
  |-- response {ch,         |                          |
  |    mac} --------------->|  store (nonce_A, mac_A)  |
  |                         |    state: WAIT_PEER      |
  |                         |                          |
  |                         |<-- join {ch,...} ---------|
  |                         |  generate nonce_B (32B)  |
  |                         |-- challenge {ch,         |
  |                         |    nonce} -------------->|
  |                         |                          |
  |                         |<-- response {ch,         |
  |                         |    mac} ----------------|
  |                         |                          |
  |  Bridge: both peers responded, exchange for mutual verification:
  |                         |                          |
  |<-- verify_peer {ch,     |-- verify_peer {ch,       |
  |  peerNonce, peerMac,    |  peerNonce, peerMac,     |
  |  peerId, peerRole}-----|  peerId, peerRole}----->|
  |                         |                          |
  |  A verifies:            |          B verifies:     |
  |  1. peerId != ownId     |  1. peerId != ownId      |
  |  2. expected =          |  2. expected =            |
  |     HMAC(encKey,        |     HMAC(encKey,          |
  |     "challenge" || ch   |     "challenge" || ch     |
  |     || peerNonce        |     || peerNonce          |
  |     || peerId           |     || peerId             |
  |     || peerRole)        |     || peerRole)          |
  |  3. mac == expected?    |  3. mac == expected?      |
  |                         |                          |
  |  Channel ACTIVE — relay begins                     |
```

##### Rejoin (After Disconnect)

When a channel transitions back to WAIT_PEER (from ACTIVE or CHALLENGING), all stored challenge data is discarded. When the departed peer re-joins, Bridge re-challenges **both** peers with fresh nonces — the remaining peer receives an unsolicited `challenge` (not preceded by `join`). The flow is identical to the initial join diagram above, with both peers proving they still hold `encKey`. A new `challenge` for a channel supersedes any pending challenge; clients MUST discard the old nonce and respond only to the latest.

##### Response Computation

```
mac = HMAC-SHA256(encKey, "challenge\0" || channelId || "\0" || nonce || "\0" || id || "\0" || role)
```

The `role` (`"initiator"` or `"responder"`) prevents reflection attacks. The nonce is generated by Bridge (32 bytes CSPRNG), ensuring freshness. Bridge cannot verify responses itself (zero-knowledge) — it only forwards them for mutual peer verification. Clients MUST reject `verify_peer` if `peerId` equals their own `id`.

Bridge-generated nonces are secure because `encKey` is unknown to Bridge — the HMAC output is computationally opaque regardless of nonce choice.

#### Channel States

```
WAIT_PEER       one peer joined and responded to challenge; waiting for second peer
CHALLENGING     both peers joined; exchanging challenge-responses and verify_peer
ACTIVE          both peers verified; relay enabled
```

Channels are created on first `join` (entering WAIT_PEER) and deleted when the last peer leaves or disconnects.

Timeouts:
- Challenge must be answered within 10 seconds, or the peer is removed from the channel
- WAIT_PEER state expires after 30 seconds (unified for both post-pairing and reconnection)

#### Channel Lifecycle

```
first join ──> WAIT_PEER ──[second join + both respond]──> CHALLENGING
                                                               |
                                                    [verify_peer delivered]
                                                               v
                                                            ACTIVE

Any state ──[peer disconnects or leaves]──> see below
Any state ──[error verify_rejected from either]──> channel deleted, both peers notified
```

| Current State | Event | Result |
|---------------|-------|--------|
| `WAIT_PEER` | Lone peer disconnects/leaves | Channel deleted |
| `CHALLENGING` or `ACTIVE` | One peer disconnects/leaves | → `WAIT_PEER`; all challenge data discarded; remaining peer notified via `peer_left`; both re-challenged when departed peer re-joins |

#### Channel Activation Timing (Implementation Note)

Bridge marks the channel as ACTIVE upon delivering `verify_peer`. Clients SHOULD buffer `message` frames received between `verify_peer` delivery and local MAC verification, then process them normally. Messages during this window are safe — an attacker without `encKey` cannot produce valid AES-GCM ciphertext.

#### Connection Replacement

If a `join` arrives for a channel where a peer with the **same `id`** already occupies a slot (e.g., client reconnects while old WebSocket is still lingering):

1. Bridge sends `{"type": "error", "code": "replaced", "ch": "<channelId>"}` to the **old** connection.
2. Bridge removes the old peer from that channel **and** removes the channelId from the old connection's `Channels` map.
3. Bridge processes the new `join` normally.

The old connection is not closed — only evicted from that specific channel. Its other channels are unaffected. Bridge MUST rate-limit `join` attempts per channelId to mitigate replacement DoS (see Bridge-Side Limits).

#### WebSocket Disconnection

When a WebSocket connection closes (cleanly or not), Bridge performs:

1. **Channels**: For each `channelId` in `Connection.Channels`, remove the peer. Channel transitions per lifecycle rules. If the other peer is still connected, send `peer_left`.
2. **Waiting peers**: Remove the peer from any pairing it was in.
3. **Connection map**: Delete the entry from `connections`.

No messages are buffered for the disconnected peer. Disconnect cleanup silently skips channelIds where the peer is no longer a member (handles races with connection replacement).

#### End-to-End Encryption

Messages are encrypted with AES-256-GCM before sending:

```
Key:    encKey (per channel, 32 bytes)
Nonce:  random 96-bit (12 bytes), generated by sender, prepended to ciphertext
AAD:    channelId (prevents cross-channel ciphertext transplant)
Format: nonce (12B) || AES-GCM(encKey, nonce, plaintext, AAD=channelId)
```

Random 96-bit nonces are safe up to ~2^32 messages per key (birthday bound). Implementations MUST use a CSPRNG for nonce generation.

#### Relay

After a channel reaches ACTIVE, peers communicate through their channelId:

```
                          channelId_1                    channelId_2
CLI                          Bridge                         App1         App2
 |                             |                              |             |
 |-- {ch:ch1,data} ---------->|-- {ch:ch1,peerId,data} ---->|             |
 |-- {ch:ch2,data} ---------->|-- {ch:ch2,peerId,data} ------------------->|
 |                             |                              |             |
 |                             |<-- {ch:ch1,data} ------------|             |
 |<-- {ch:ch1,peerId,data} ---|                              |             |
```

### Message Format

All messages are JSON over WebSocket (text frames). The `ch` field carries pairingId (during pairing) or channelId (during relay) — `type` disambiguates. Bridge never interprets `data`.

All binary fields (`pubShare`, `nonce`, `mac`, `data`) are encoded as **unpadded base64url** (RFC 4648 §5). `pubShare` uses uncompressed SEC1 encoding (`0x04 || x || y`, 65 bytes for P-256).

| Type | Direction | Fields | Description |
|------|-----------|--------|-------------|
| `pair` | C→B | `ch`, `pubShare`, `id` | Initiate pairing |
| `pair_matched` | B→C | `ch`, `pubShare`, `id`, `role` | Peer matched |
| `join` | C→B | `ch`, `id` | Join channel |
| `challenge` | B→C | `ch`, `nonce` | Challenge for channel join |
| `response` | C→B | `ch`, `mac` | Challenge response |
| `verify_peer` | B→C | `ch`, `peerNonce`, `peerMac`, `peerId`, `peerRole` | Peer's challenge data for mutual verification |
| `message` | C→B | `ch`, `data` | Send encrypted message |
| `message` | B→C | `ch`, `peerId`, `data` | Forwarded encrypted message |
| `leave` | C→B | `ch` | Leave channel |
| `peer_left` | B→C | `ch`, `peerId` | Peer disconnected or left |
| `error` | Both | `code`, `ch`(optional), `message` | Error (see below) |

If either peer rejects verification, it sends `error` with `code: "verify_rejected"` and `ch` (required). Bridge clears the channel and notifies the other peer.

### Message Routing and Delivery

```
switch msg.type:
  "pair"          -> pairing logic (route by ch as pairingId)
  "join"          -> begin challenge-response for channel
  "response"      -> store response, trigger verify_peer when both ready
  "error"         -> if code=="verify_rejected": clear channel, notify peers
  "leave"         -> remove peer from channel, send peer_left to other peer
  "message"       -> relay to the other peer in channel (by ch)
```

Bridge is fire-and-forget: messages are forwarded only if the target peer is connected and the channel is ACTIVE. No buffering, no acknowledgments. Reliable delivery is the responsibility of the application layer.

### Error Codes

| Code | Phase | Direction | Description |
|------|-------|-----------|-------------|
| `invalid_message` | Both | B→C | Malformed JSON or missing required fields |
| `pairing_expired` | Pair | B→C | No matching peer joined within PairingTTL |
| `channel_full` | Relay | B→C | Channel already has 2 peers |
| `channel_not_found` | Relay | B→C | Channel does not exist |
| `not_in_channel` | Relay | B→C | Sender has not joined this channel |
| `challenge_timeout` | Relay | B→C | Peer did not respond to challenge within 10 seconds |
| `verify_rejected` | Relay | Both | Peer rejected verification; channel deleted |
| `replaced` | Relay | B→C | Another connection joined with the same id |
| `rate_limited` | Both | B→C | Rate exceeded |

Connection-level errors close the WebSocket. Channel-level errors only remove the peer from that channel — other channels on the same connection are unaffected.

## Reconnection

Clients store channelId, encKey, role, and id locally. On reconnect, they open a new WebSocket and send `join` for each channel. The same challenge-response protocol is used — no separate reconnect token. The protocol works identically whether Bridge has restarted or not.

```
Bridge restarts (memory cleared)
  channels = {}

CLI reconnects:  WS /v1/connect
  -> join {"ch":"abc123","id":"sess-abc"}
  <- challenge {"ch":"abc123","nonce":"..."}
  -> response {"ch":"abc123","mac":"..."}
  -> channels["abc123"] = [cli_conn], state: WAIT_PEER

App reconnects:  WS /v1/connect
  -> join {"ch":"abc123","id":"device-xyz"}

  Bridge: second peer joining, re-challenge both:
  <- challenge {"ch":"abc123","nonce":"..."} to App
  <- challenge {"ch":"abc123","nonce":"..."} to CLI (fresh nonce)

  CLI responds, App responds.
  Bridge sends verify_peer to both peers, channel -> ACTIVE

-> Communication restored.
```

On WebSocket close or challenge timeout, clients SHOULD:

1. Wait 1-2 seconds before reconnecting (avoid thundering herd).
2. Open a new WebSocket to `/v1/connect`.
3. Send `join` for each stored channelId. Order does not matter.

## Keepalive

Bridge uses WebSocket-level ping frames (RFC 6455) with a read deadline of `IdleTimeout` (60s), reset on every received message or pong frame. No application-level keepalive messages are needed.

## Security

### Why SPAKE2

Plain X25519 + verify is vulnerable to MITM brute-force: a malicious Bridge could substitute public keys, establish two separate shared keys, then try all possible 8-character codes offline by checking verify hashes. With 31^8 ~ 852 billion candidates, this takes ~minutes on modern GPUs.

SPAKE2 eliminates this attack class entirely. The password (pairing code) is embedded into the key exchange via blinding with constant points M and N (defined in RFC 9382). Without knowing the code, an attacker cannot unblind the exchanged values and computes a completely different shared key.

SPAKE2 over P-256 is chosen for portability: P-256 is natively supported by virtually all cryptographic libraries and hardware security modules, including IoT platforms (ESP32 mbedtls, STM32 CryptoLib), mobile (CryptoKit, BouncyCastle), and browsers (Web Crypto API).

**Note:** The implementation uses a symmetric SPAKE2 variant where both peers blind with M (not M/N as in RFC 9382). This is because the pubShare must be sent before the server assigns roles. Role differentiation is achieved through the TT transcript (idProver/idVerifier ordering) rather than distinct blinding points. This avoids an extra round-trip for role assignment, which is significant for IoT devices where PBKDF2 + SPAKE2 already takes 10+ seconds.

### Why PBKDF2 for pairingId

The pairingId must be computable by both peers from the shared pairing code so they can find each other. A naive derivation like `HMAC(code, "room")` would allow the Bridge to brute-force the code from the pairingId in minutes on a GPU, then perform a SPAKE2 MITM attack.

PBKDF2-SHA256 with 100,000 iterations makes each candidate evaluation cost ~5-20ms on desktop hardware, rendering brute-force infeasible within PairingTTL. A time-varying salt (`"latch-relay-room-v1" || window`) invalidates precomputed tables every 10 minutes.

PBKDF2 is chosen over memory-hard functions (Argon2id, scrypt) for portability: it requires <1KB of RAM and is available on all platforms including IoT devices. Security relies on the combination of pairing code entropy (31^8 ≈ 39.6 bits), 100K iterations, time-varying salt, and short PairingTTL (10 min). Within PairingTTL, even 1000 high-end GPUs can cover less than 0.01% of the search space.

**Performance**: ESP32-S3 (hardware SHA-256): ~3-5 seconds per derivation. Base ESP32 (software SHA-256): ~6-10 seconds. Worst case with window fallback: ~12-20 seconds on base ESP32.

**Security boundary**: PBKDF2 does not resist ASIC acceleration. However, the time-varying salt forces real-time computation, and the 10-minute PairingTTL limits the attack window.

### Zero-Knowledge Guarantees

| Attack | Result |
|--------|--------|
| Read message content | Only ciphertext visible; no encKey to decrypt |
| Pair wrong peers | Different ISK → different channelId → peers never meet; join times out |
| MITM (substitute public shares) | Without code, attacker computes wrong shared secret; challenge-response fails |
| Brute-force code from pairingId | PBKDF2 100K iterations + time-varying salt: infeasible within PairingTTL |
| Precompute rainbow table | Time-varying salt invalidates tables every 10 minutes |
| Replay old public shares | Random scalars differ each session; replayed shares produce wrong ISK |
| Read history after restart | No persistence; no history exists |
| Join channel with leaked channelId | Challenge-response requires encKey; attacker cannot respond |
| Forge messages on channel | AES-GCM verification (AAD=channelId) fails; receiver discards |
| Occupy channel slot (DoS) | Mutual verification detects attacker within one RTT; channel cleared |
| Pairing squatting (DoS) | Must brute-force PBKDF2 to guess pairingId; even if observed, cannot complete SPAKE2 without code; MaxPairingsPerIP limits attempts |
| Tamper with peer IDs | Modified IDs → different SPAKE2 transcripts → different ISK → pairing fails |
| Connection-replacement DoS | Cannot complete challenge-response without encKey; mitigated by per-channelId join rate limiting |

### Known Limitations

| Limitation | Description |
|------------|-------------|
| **Traffic analysis** | Bridge can observe message timing, sizes, and which connections share channels. Reveals topology without content. Inherent to relay architecture. |
| **No forward secrecy** | `encKey` is static per channel. If compromised, past recorded messages can be decrypted. No ratcheting. |
| **Channel existence oracle** | An attacker with a `channelId` can probe whether the channel is active. Cannot join without `encKey`. |

### Bridge-Side Limits

```go
MaxPeersPerChannel  = 2        // 1:1 channels, at most 2 peers
MaxChannelsTotal    = 10000    // global channel cap (configurable)
PairingTTL          = 10min    // waiting peer expiration (deleted on successful pairing)
IdleTimeout         = 60s      // close connection if no activity
MaxMessageSize      = 20MB     // reject oversized WebSocket messages
ChallengeTimeout    = 10s      // challenge response deadline
WaitPeerTimeout     = 30s      // WAIT_PEER state expiration

// Per-IP rate limits (per window)
MaxPairingsPerIP    = 60/min   // pairing attempts from same IP
MaxChannelsPerIP    = 30/min   // channel joins from same IP
MaxConnectionRate   = 10/s     // new connections per second from same IP
MaxJoinsPerChannel  = 3/10s   // join attempts per channelId (mitigates replacement DoS)
```

## Cryptographic Dependencies

Bridge itself performs no cryptographic operations — only matching, forwarding, and generating random nonces (CSPRNG).

Client-side primitives:

| Primitive | Usage | Portability |
|-----------|-------|-------------|
| PBKDF2-SHA256 | Seed derivation (100K iterations) | All platforms, including IoT |
| P-256 (secp256r1) | SPAKE2 elliptic curve operations | All TLS libraries, hardware-accelerated on many MCUs |
| SPAKE2 (RFC 9382) | Password-authenticated key exchange | ~400-800 lines on top of P-256 (including point validation and constant-time safeguards); no built-in IoT library |
| HKDF-SHA256 | Key derivation (ISK, channelId, encKey) | All platforms |
| HMAC-SHA256 | Challenge-response authentication | All platforms |
| AES-256-GCM | Message encryption (AEAD, AAD=channelId) | All platforms, hardware-accelerated on many MCUs |

Reference implementations:

| Platform | SPAKE2 / P-256 | PBKDF2 | HKDF + AEAD |
|----------|----------------|--------|-------------|
| Go | `golang.org/x/crypto` (P-256 in stdlib) | `golang.org/x/crypto/pbkdf2` | stdlib `crypto` |
| Rust | `spake2` crate + `p256` crate | `pbkdf2` crate | `hkdf` + `aes-gcm` crates |
| Swift | `CryptoKit` (P-256 native) | `CommonCrypto` or `CryptoKit` | `CryptoKit` |
| TypeScript | `@noble/curves` (P-256) | `node:crypto` / Web Crypto API | `node:crypto` / Web Crypto API |
| C / IoT | `mbedtls` or `wolfSSL` (P-256) | `mbedtls` / `wolfSSL` | `mbedtls` / `wolfSSL` |
| Python | `cryptography` library | `hashlib.pbkdf2_hmac` | `cryptography` |
